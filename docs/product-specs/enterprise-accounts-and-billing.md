# 企业账户、角色、计费与 API Key 产品规格

状态：产品边界已确认；B、C2、D、E 已受控整合，企业发布门保持关闭，跨数据库与 UAT 验收尚未完成

版本：v1.0

确认日期：2026-08-17

## 1. 文档目的

本规格定义平台 Root、平台管理员、企业管理员、企业成员和个人用户之间的身份、权限、企业归属、计费、额度、邀请、API Key、邮件交付、成员暂停与移除边界。

本规格是本次企业账户需求的权威产品边界。涉及企业成员、Root/Admin 多 Key 定向轮换、重置后邮件明文交付等规则时，本规格优先于既有 [`single-primary-api-key-account.md`](single-primary-api-key-account.md) 的默认建议；既有密码、OAuth、Passkey、2FA 等登录能力保持不变。

本文只定义产品行为和验收条件，不代表源码、数据库迁移、支付回调、SMTP 或跨数据库并发已经实现或验证。

## 2. 问题与目标

### 2.1 当前问题

- Root 与平台管理员的业务管理权限不平级，部分系统能力仍为 Root 专属。
- 平台管理员身份、企业管理员身份和普通用户身份容易被混入同一个数值角色，存在平台越权风险。
- 当前计费主体主要是用户，不能稳定表达企业钱包、成员分配额度、在途预留、企业账单和退出后的迟到退款。
- 当前邀请是平台注册邀请，不是企业成员邀请，且不能覆盖已有用户加入企业。
- 当前用户全局状态不能表达“只暂停企业资助调用”。
- 当前 Token 剩余额度可以被用户更新，不能直接作为企业成员的硬额度。
- API Key 同时承担 API 调用和后台登录凭据，重置、邮件交付和 Root/Admin 多 Key行为需要明确边界。

### 2.2 产品目标

1. Root 与平台管理员在业务管理能力上平级，同时保护同级管理员的身份和认证信息。
2. 将平台身份和企业身份拆开，企业管理员不得获得平台管理员权限。
3. 为每个企业建立独立计费主体，实现企业钱包、成员真实划转额度、预留、结算、回收和审计。
4. 支持企业管理员邀请新用户或已有用户成为企业成员。
5. 支持企业管理员暂停、恢复和安全移除成员，不影响成员的平台身份和个人资产。
6. 普通用户、企业管理员和企业成员只拥有一个主 API Key；Root/Admin 保留多 Key。
7. API Key 重置只轮换选定 Key，重置成功后通过绑定邮箱明文发送完整新 Key。
8. 历史账单在成员退出、换企业、Key 轮换后仍保持原企业和原成员归属。

### 2.3 成功结果

- 企业管理员只能管理本企业，无法访问平台管理能力或其他企业资源。
- 成员消费不会超过可用企业分配额度，也不会回退扣除个人钱包或个人订阅。
- 企业资金在分配、预留、结算、退款和回收后保持可解释、可核对、可审计。
- 成员退出不会产生错扣、错退、重复退款或历史账单漂移。
- Key 重置不会新增第二条有效 Key，不会通过重置恢复额度或绕过企业策略。

当前业务基线和目标数值均为 `UNKNOWN`；上线前需补充企业邀请成功率、额度异常率、移除人工处理率和邮件待交付率等指标。

## 3. 术语

| 术语 | 定义 |
| --- | --- |
| 平台身份 | 决定是否能访问全平台管理能力，取值为 Root、Admin、User。 |
| 企业身份 | 用户在唯一企业内的身份，取值为 Owner、Member。 |
| Root | 平台初始化和兼容性保留身份；业务管理能力与 Admin 平级。 |
| 平台管理员/Admin | 管理全平台业务配置和用户，但不能修改其他 Root/Admin 的身份与认证信息。 |
| 企业管理员/Owner | 企业唯一所有者，平台身份仍可为普通 User；不是平台 Admin。 |
| 企业成员/子账号 | 被企业邀请并接受的独立平台用户，通过自己的主 Key 消费企业分配额度。 |
| 个人用户 | 没有有效企业关系的普通平台用户。 |
| 企业钱包 | 企业拥有的资金账户和唯一企业计费主体。 |
| 企业可分配余额 | 尚未划转给成员且未被 Owner 请求预留的企业钱包余额。 |
| 成员分配额度 | 从企业可分配余额真实划转并为指定成员保留的额度。 |
| 成员在途额度 | 已为同步请求或异步任务预留、尚未最终结算的成员额度。 |
| Key 自设上限 | 用户对自己当前 Key 设置的自我消费保护，不是资金账户或企业授权额度。 |
| 管理视图 | Root/Admin 使用的平台管理导航和展示上下文。 |
| 企业视图 | Owner/Member 使用的企业导航和展示上下文。原“用户模式”统一称为企业视图。 |
| 注册邀请 | 邀请尚未注册的邮箱创建平台账户。 |
| 企业邀请 | 邀请新用户或已有用户加入指定企业。 |
| 待交付 | Key 已完成数据库轮换、旧 Key 已失效，但新 Key 邮件尚未成功提交或最终投递的状态。 |
| 异常账 | 实际费用异常超过已预留额度时，记录在原企业名下、但不扣个人资产的独立账务记录。 |

## 4. 身份模型与角色关系

### 4.1 两个独立维度

平台身份和企业身份必须独立表达：

```text
platform_role:
  ROOT | ADMIN | USER

enterprise_membership.role:
  OWNER | MEMBER
```

不得新增一个位于现有平台数值角色序列中的 `EnterpriseAdmin`。对外产品可以展示“企业管理员”，内部应由企业 Owner 关系表达。

### 4.2 角色矩阵

| 产品角色 | 平台身份 | 企业身份 | Key 数量 | 可见视图 | 模型调用计费主体 |
| --- | --- | --- | --- | --- | --- |
| Root | ROOT | 自己独立企业的 OWNER | 多 Key | 管理视图、企业视图 | 自己的企业钱包 |
| 平台管理员 | ADMIN | 自己独立企业的 OWNER | 多 Key | 管理视图、企业视图 | 自己的企业钱包 |
| 企业管理员 | USER | 唯一企业的 OWNER | 一个主 Key | 企业视图 | 自己的企业钱包 |
| 企业成员 | USER | 唯一企业的 MEMBER | 一个主 Key | 企业视图 | 自己的成员分配额度，最终归企业账单 |
| 个人用户 | USER | 无有效企业关系 | 一个主 Key | 个人视图 | 个人钱包或个人订阅 |

### 4.3 Root/Admin 独立企业自动创建

- 每个 Root/Admin 都拥有一个互不共享的独立企业，并成为该企业唯一 Owner。
- 新建或升级为 Root/Admin 时，应原子创建企业和 Owner 关系。
- 既有 Root/Admin 上线迁移时必须幂等补建；重复执行不能创建第二个企业。
- 模型调用发生时如果企业关系缺失，应创建或修复企业关系；失败时必须拒绝调用，不得回退到个人钱包。
- Root/Admin 的模型调用始终扣自己的企业钱包，与当前显示管理视图还是企业视图无关。
- 平台管理接口不产生模型消费，不进入企业计费。

### 4.4 普通用户成为企业管理员

- 平台 Root/Admin 可以将一个未加入任何企业的普通用户设置为企业管理员。
- 该操作创建一个新企业，并将用户设置为该企业唯一 Owner。
- 用户的平台身份仍为 `USER`，不能改成平台 `ADMIN`。
- 用户已有个人余额和个人订阅在成为 Owner 后冻结。
- 用户已经属于其他企业时，必须先完成原企业退出或移除流程，不能直接覆盖企业关系。

### 4.5 唯一 Owner

- 每个企业任何时刻必须且只能有一个 Owner。
- Owner 不能直接退出、移除或删除，避免企业成为无主状态。
- Owner 需要离开时，必须先完成所有权转移或关闭企业。
- 如果首版不提供所有权转移，则只能在成员、在途请求、异常账和可退款事项全部清理后关闭企业。
- Root/Admin 被降级为普通用户时，平台身份变化不自动删除其企业；该用户继续作为企业 Owner，即产品上成为企业管理员。
- 任何 Owner 的全局禁用或删除，都必须先处理企业所有权或企业关闭，不能留下无主企业。

## 5. 管理视图与企业视图

- 管理视图和企业视图只控制前端导航、展示和默认操作上下文。
- 当前版本不把视图作为接口安全边界，这是已接受的产品风险。
- Root/Admin 切换到企业视图后，其平台身份不会下降，技术上仍可调用其已有权限允许的平台管理接口。
- 计费不能读取前端视图状态，也不能由客户端传入视图决定。
- 平台管理接口按平台身份授权；企业接口按服务端解析出的企业关系授权。
- 企业接口的 `enterprise_id` 不能仅信任请求参数，必须与当前有效企业关系绑定校验。

## 6. 权限边界

### 6.1 Root 与平台管理员

Root 与 Admin 对以下业务管理能力平级：

- 渠道管理。
- 模型管理。
- 用户管理。
- 兑换码管理。
- 订阅管理。
- 系统信息。
- 系统设置。
- 将符合条件的用户设置为企业管理员。

同级身份保护规则：

- Root/Admin 不能修改其他 Root/Admin 的平台角色、邮箱、密码、Passkey、2FA、OAuth 绑定、API Key、登录会话或全局状态。
- Root/Admin 可以通过自助流程修改自己的认证信息。
- 平台管理员身份的创建、初始化和灾难恢复继续沿用现有平台治理；不得借本需求放宽同级身份保护。
- Root/Admin 可以互相调整对方企业的额度，无需审批。
- “不能给自己加额度”只是统计约定，不是安全边界，也不作为后端拒绝条件。
- 所有人工调额必须记录操作者、受益企业、变更前后额度、原因、请求 ID 和时间。

### 6.2 企业管理员

企业管理员只能管理自己所属且担任 Owner 的企业，可以：

- 邀请新用户或已有用户成为企业成员。
- 撤销未接受的企业邀请。
- 查看本企业成员及成员状态。
- 为成员分配、追加和回收未消费额度。
- 设置成员企业调用白名单。
- 查看企业钱包、成员用量、企业账单和异常账。
- 暂停和恢复成员的企业资助调用。
- 在满足回收与结算条件后移除成员。
- 使用企业支付和账单能力为企业钱包入账。

企业管理员不能：

- 获得平台管理权限。
- 查看或操作其他企业。
- 全局封禁、删除或修改成员的平台身份。
- 查看、接收或代为重置成员完整 API Key。
- 查看、回收或消费成员个人余额及个人订阅。
- 将企业成员额度转成自己的个人资产。
- 修改企业历史账单的原始归属。

### 6.3 企业成员

企业成员可以：

- 使用自己的唯一主 API Key 发起企业资助的模型调用。
- 查看自己的企业成员状态、分配额度、已用额度和企业资助调用记录。
- 重置自己的主 API Key。
- 设置、降低或重新调高自己的 Key 自设上限，但不能超过可用成员分配额度。
- 在被暂停后继续登录、验证邮箱、找回或重置 Key、查看状态和历史。

企业成员不能：

- 管理其他成员或查看其他成员数据。
- 修改企业钱包或自己的成员硬额度。
- 将 Key 设置为无限额度。
- 通过 Key 设置扩大企业管理员配置的白名单。
- 充值、购买或续费个人订阅。
- 在企业额度不足时回退使用个人钱包或个人订阅。

### 6.4 个人用户

- 没有有效企业关系。
- 使用一个主 API Key。
- 可以使用自己的个人钱包和个人订阅。
- 可以按平台既有规则充值、购买订阅和接受企业邀请。
- 接受企业邀请后，个人资产转为冻结状态，但所有权仍属于本人。

### 6.5 权限矩阵

| 能力 | Root/Admin 管理视图 | Root/Admin 企业视图 | 企业管理员 | 企业成员 | 个人用户 |
| --- | --- | --- | --- | --- | --- |
| 平台业务管理 | 是 | 已接受风险：平台身份仍允许 | 否 | 否 | 否 |
| 管理本企业成员 | 否，除非进入自己的企业能力 | 是 | 是 | 否 | 否 |
| 分配/回收成员额度 | 否，除平台人工调账 | 是 | 是 | 否 | 否 |
| 暂停成员企业调用 | 否，除平台治理动作 | 是 | 是 | 否 | 否 |
| 全局封禁平台用户 | 按平台权限 | 按平台权限 | 否 | 否 | 否 |
| 企业充值/账单 | 自己企业 | 自己企业 | 自己企业 | 否 | 否 |
| 个人充值/订阅 | 个人资产冻结 | 个人资产冻结 | 个人资产冻结 | 否 | 是 |
| 重置自己的 Key | 定向选择 Key | 定向选择 Key | 唯一主 Key | 唯一主 Key | 唯一主 Key |

## 7. 企业与成员关系

### 7.1 唯一企业约束

- 一个用户同一时间最多属于一个企业。
- `OWNER`、`ACTIVE`、`PAUSED`、`DRAINING` 等未结束关系都占用唯一企业名额。
- 可以同时收到多个待处理邀请，但只能成功接受一个。
- 并发接受多个企业邀请时，只有第一个事务成功，其余必须失败或失效。
- 用户退出旧企业并完成全部结算后，才能接受新企业邀请。

### 7.2 注册邀请与企业邀请

两类邀请必须分别建模：

| 类型 | 目标 | 结果 |
| --- | --- | --- |
| 注册邀请 | 尚未注册的邮箱 | 创建平台用户和主 Key，不天然代表企业关系。 |
| 企业邀请 | 新邮箱或已有平台用户 | 接受后创建指定企业的 Member 关系。 |

企业邀请规则：

- 邀请必须绑定企业、目标邮箱、邀请人、预期成员角色、有效期和状态。
- 企业管理员只能从自己的企业发出邀请。
- 已有用户接受邀请时，登录用户的已验证邮箱必须与邀请邮箱匹配。
- 新用户接受企业邀请时，账户创建、唯一主 Key 创建、邀请消费和成员关系创建必须原子完成。若当时 `QuotaForNewUser` 大于 0，仍按平台既有新用户规则发放该默认赠额。
- 企业邀请产生的默认赠额是新用户本人的个人资产，不进入企业钱包、不形成成员额度，企业管理员不可见、不可消费也不可回收；用户加入企业期间该赠额立即冻结，离开企业后按普通个人资产规则恢复可用。
- 接受时再次检查用户没有其他有效企业关系。
- 邀请可被撤销、拒绝或过期；失效邀请不能重复使用。
- 企业邀请不能复用推广邀请字段，也不能触发推广奖励。

### 7.3 成员状态机

```text
INVITED
  ├─ 接受且未属于其他企业 → ACTIVE
  ├─ 拒绝/撤销/过期 → CLOSED
  └─ 接受冲突 → REJECTED

ACTIVE
  ├─ 企业管理员暂停 → PAUSED
  └─ 发起移除 → PAUSED → DRAINING

PAUSED
  ├─ 企业管理员恢复 → ACTIVE
  └─ 发起移除 → DRAINING

DRAINING
  ├─ 仍有在途请求/任务 → 保持并等待
  ├─ 超时 → MANUAL_REVIEW
  └─ 在途归零并回收完成 → RECLAIMED

RECLAIMED
  └─ 原子关闭关系 → REMOVED

REMOVED
  └─ 用户恢复个人资产使用，可接受新企业邀请
```

### 7.4 暂停成员

- 暂停只修改企业成员关系，不修改平台用户全局状态。
- 暂停后立即拒绝新的企业资助 API 预留和异步任务提交。
- 已经开始的同步请求、异步任务、结算和退款继续按原快照完成。
- 暂停不阻止后台登录、邮箱验证、Key 重置、查看自己状态和历史。
- 暂停不自动回收额度；回收是独立的企业账务动作。

### 7.5 移除成员

移除必须按以下顺序执行：

1. 将成员置为 `PAUSED`，阻断新的企业资助调用。
2. 进入 `DRAINING`，等待同步请求、异步任务、预扣、结算和退款完成。
3. 只回收成员未消费且未预扣的可用额度。
4. 确认成员可用额度为零、在途额度为零，且不存在未结算任务。
5. 将额度账户标记为 `RECLAIMED`。
6. 原子关闭成员关系并进入 `REMOVED`。
7. 解冻用户个人钱包和个人订阅。

任何一步未完成都不能先把用户变回个人用户。等待超时后进入人工处理，不得自动忽略在途账务。

### 7.6 迟到退款

- 所有退款按请求创建时的计费快照处理。
- 成员额度账户仍可用时，退款退回原成员可用额度。
- 成员额度账户已经关闭时，退款退回原企业钱包。
- 任何情况下都不能因为用户已经恢复为个人用户而退款到个人钱包。

## 8. 企业钱包与成员额度

### 8.1 计费主体

至少存在以下独立计费对象：

```text
PersonalBillingAccount(user_id)
EnterpriseBillingAccount(enterprise_id)
EnterpriseMemberAllocation(membership_id)
```

- 个人用户调用：计入个人计费账户。
- 企业 Owner 调用：直接计入企业钱包。
- 企业成员调用：扣成员分配额度，最终计入所属企业账单。
- 企业调用禁止回退个人钱包或个人订阅。
- 首版只共享企业钱包额度，不共享任何个人或企业订阅。

### 8.2 真实划转与预留

成员分配额度是企业资金的真实划转/预留，不是只用于展示的软上限：

```text
企业入账：
企业可分配余额 += X

分配给成员：
企业可分配余额 -= X
成员可用额度 += X

请求预留：
成员可用额度 -= X
成员在途额度 += X

正常结算：
成员在途额度 -= 预留额
成员累计消费 += 实际费用
多预留部分退回成员可用额度

失败退款：
成员在途额度 -= X
成员可用额度 += X

回收：
成员可用额度 -= X
企业可分配余额 += X
```

企业账面守恒：

```text
企业净入账 - 已结算正常消费
= 企业可分配余额
 + Owner 在途额度
 + 全体成员可用额度
 + 全体成员在途额度
```

### 8.3 额度不变量

- 企业可分配余额、成员可用额度和成员在途额度不得为负数。
- 分配、回收、预留、结算和退款必须是原子操作。
- 每个账务动作必须有唯一业务幂等键和不可变流水。
- 企业管理员只能回收成员可用额度，不能回收在途额度或已消费额度。
- 企业可分配余额不能重复包含已经划转给成员的额度。
- 成员企业调用必须经过预留，不得使用“额度充足所以跳过预扣”的信任旁路。
- 企业额度不足、成员额度不足或成员状态非 `ACTIVE` 时，拒绝新的企业资助调用。
- 企业管理员追加额度不能自动清除成员自己设置的更低 Key 上限。

### 8.4 异常超额

当实际上游费用异常超过已预留额度时：

- 正常预留部分按原请求快照结算。
- 超出部分记入原企业的独立异常账。
- 不扣成员个人余额、个人订阅或其他个人资产。
- 不把企业可分配余额或成员额度写成负数。
- 立即暂停该成员后续企业资助调用。
- Owner 自己的调用发生异常超额时，暂停 Owner 的后续模型调用，但不影响平台管理接口。
- 异常账进入人工核对；处理、减免或补扣必须产生新的冲正流水，不能修改原始消费记录。

### 8.5 充值、订阅与其他个人入账

- 企业 Owner 发起支付时，订单计费主体必须是企业，支付成功进入企业钱包。
- 企业成员不得新建个人充值订单，不得购买或续费个人订阅；后端必须拒绝。
- 用户加入企业前已经创建的个人支付订单，在加入后收到支付回调时，仍按订单创建时快照进入冻结的个人钱包。
- 签到、兑换码、推广奖励等个人入账如果平台继续保留，只能进入冻结的个人钱包，不能转换成企业钱包或成员额度。
- 企业管理员不可见、不可回收上述个人资产。

## 9. 个人资产冻结

### 9.1 冻结范围

用户成为企业 Owner 或 Member 后：

- 个人钱包保留所有权和账面余额，但禁止用于模型调用。
- 个人订阅保留所有权，但禁止使用。
- 企业管理员不可见、不可回收、不可消费这些个人资产。
- 历史个人账单继续归用户本人，不并入企业账单。

Root/Admin 自动拥有独立企业后，其已有个人钱包和个人订阅也遵守相同冻结规则；其模型调用只使用企业钱包。

### 9.2 订阅有效期暂停

- 个人订阅冻结期间，有效期同步暂停。
- 冻结开始时记录冻结时间；解除冻结时按实际冻结时长顺延到期时间。
- 多次加入和退出产生的冻结时长累计计算。
- 冻结期间不得发生订阅用量周期重置、自动消费或用户主动续费。
- 解冻后从冻结前剩余有效期和剩余用量继续使用。
- 解冻、顺延和周期恢复必须有审计记录并可重复执行而不重复延长。

## 10. API Key 产品边界

### 10.1 Key 数量

- 普通个人用户：一个主 API Key。
- 普通企业管理员：一个主 API Key。
- 企业成员：一个主 API Key。
- Root/Admin：保留现有多 Key能力。
- 企业关系变化不创建第二个 Key，也不自动轮换现有 Key。
- 普通用户的主 Key只能重置，不能删除或禁用到零条有效 Key。

### 10.2 Key 与登录

- 主 API Key可以作为后台登录身份证明，也可用于 API调用。
- API Key不是唯一后台登录方式；密码、OAuth、Passkey、2FA等既有方式不在本需求中修改。
- API调用额度耗尽不能阻止后台登录。
- API调用用的额度、模型或白名单限制不能错误地成为后台登录限制。
- Root/Admin现有每一条有效 API Key都可登录后台，这是已接受风险，本期不处理。

### 10.3 Key 自设上限

Key 自设上限是用户自我保护，不是企业硬额度：

```text
企业成员有效可调用额度 =
min(
  成员可用分配额度,
  Key 自设剩余上限
)
```

- 用户可以降低自设上限，也可以重新调高。
- 企业成员调高后仍不能超过当前成员可用分配额度。
- 自设上限不能写入或覆盖成员资金账户。
- 设置上限不能清零累计已用量、产生退款或恢复已消费额度。
- 企业成员不能设置无限 Key。
- Key 重置必须继承自设上限、累计用量、企业白名单和其他现有策略。

### 10.4 定向轮换

- 重置哪个 Key，就只轮换哪个 Key。
- Root/Admin重置时必须明确选择目标 Key；其他 Key保持不变。
- 普通用户只有一个主 Key，目标 Key唯一。
- 轮换在原 Token 身份上进行，保留 Token ID、额度、用量、名称、模型限制、IP/白名单、企业关系和历史账单关联。
- 轮换成功后目标旧 Key立即失效，不能继续调用 API或登录。
- 至少撤销所有由目标 Key建立的后台会话；如果当前会话无法可靠识别来源，技术设计可选择撤销该账号全部后台会话，但不能少撤销。
- 其他未被选择的 Root/Admin Key及其正常状态保持不变。
- “定向轮换”不等同于账号整体失窃处置；其他Key仍有效属于保留多Key能力的已接受风险。

### 10.5 重置前验证

- 已登录主动重置不能只依赖当前 Session，必须完成现有安全验证，例如邮箱验证码、密码、Passkey或2FA中的受支持方式。
- 未登录邮箱找回必须先验证绑定邮箱所有权。
- Root/Admin未登录找回时，只能在邮箱验证成功后查看掩码 Key列表并选择目标Key。
- 不能仅凭邮箱地址、Key ID、Key名称或掩码前缀直接触发轮换。
- 找回入口对存在和不存在的邮箱使用一致公开响应，避免账户枚举。
- 并发点击、请求重试和邮件重试必须由同一幂等键收敛到一次轮换。

### 10.6 明文邮件交付

重置成功后，新完整 Key直接写入用户已验证绑定邮箱的邮件正文：

- 该规则适用于普通用户、企业管理员、企业成员、Root和Admin。
- 收件邮箱不能由请求参数临时覆盖。
- 企业管理员或平台管理员不能代收其他用户的新 Key。
- 管理页面、普通列表接口、URL、应用日志、错误响应和审计详情不得回显完整 Key。
- 邮件队列和投递日志不得把完整 Key写入普通可检索日志。
- 数据库轮换与外部 SMTP投递无法组成原子事务，产品方已明确接受该风险。

### 10.7 待交付状态

轮换与邮件交付顺序如下：

```text
安全验证成功
→ 原子轮换目标 Key
→ 旧 Key失效
→ 生成一条绑定轮换结果的邮件交付任务
→ 尝试发送同一个新 Key
```

- 数据库轮换提交后，新 Key是唯一权威Key；SMTP失败不能重新启用旧Key。
- SMTP失败时账户/目标Key进入可审计的 `PENDING_DELIVERY` 或 `FAILED_DELIVERY` 状态。
- 用户或系统重试只能重发同一个新Key，不能再次轮换。
- 一次用户动作最多产生一次Key轮换。
- SMTP返回成功只代表邮件已提交给邮件服务商，不能宣称用户已实际收到。
- 最终投递失败时允许用户重新完成邮箱验证后重发同一个新Key。
- 重发能力不得向管理员展示完整Key。

## 11. 白名单与企业策略

- 企业管理员为成员设置的白名单是企业资助调用的硬约束。
- 企业成员不能通过自己的Key设置扩大企业白名单。
- 如果保留用户自己的更严格Key白名单，则实际允许范围取企业白名单与用户Key白名单的交集。
- 成员退出企业后，企业策略自动失效，不能永久污染用户个人Key策略。
- Key重置必须继承当前有效企业策略，不能借轮换绕过暂停或白名单。
- 后台登录不使用API调用白名单作为认证条件。

## 12. 账单、快照与审计

### 12.1 请求和账单快照

每笔请求、异步任务、订单、结算、退款和冲正创建时至少固化：

```text
actor_user_id
enterprise_id
membership_id
billing_account_id
allocation_id
token_id
request_id
funding_source
membership_role_snapshot
```

- 后续结算和退款只能使用创建时快照，不能根据用户当前企业关系重新推断。
- 成员退出、加入新企业、Key重置、企业关闭或用户更名不能改写历史归属。
- 删除或关闭业务对象不能物理删除财务流水。

### 12.2 企业可见范围

企业管理员可以查看：

- 成员身份和成员状态。
- 分配、预留、消费、回收和退款金额。
- 调用时间、模型、Token名称或掩码标识、请求ID和计费结果。
- 企业钱包入账、企业账单和异常账。

企业管理员不能查看：

- 成员完整 API Key。
- 成员密码、Passkey、2FA、OAuth等认证材料。
- 成员个人钱包、个人订阅和个人账单。
- 未经产品另行授权的请求正文、提示词或响应正文。

### 12.3 财务流水与操作审计

- 额度流水是不可变财务记录，必须与余额变更处于同一事务。
- 操作审计记录谁在何时对哪个企业或成员执行了什么动作。
- 邀请、接受、暂停、恢复、分配、回收、移除、Owner变更、调额、Key轮换、邮件失败和人工异常处理都必须审计。
- 异步操作日志不能代替财务流水。
- 审计至少记录操作者、企业、目标成员、动作、变更前后值、请求ID、结果和失败原因。

## 13. 核心用户流程

### 13.1 平台管理员设置企业管理员

1. Root/Admin选择一个未加入企业的普通用户。
2. 系统确认该用户不是Root/Admin，且没有有效企业关系。
3. 原子创建企业和唯一Owner关系。
4. 冻结该用户个人钱包和个人订阅。
5. 用户下次进入后台时显示企业视图和企业管理能力。
6. 用户平台身份仍为普通User。

### 13.2 企业管理员邀请已有用户

1. Owner填写已有用户的已验证邮箱并发送企业邀请。
2. 系统创建绑定企业和邮箱的一次性邀请。
3. 用户登录并确认接受。
4. 系统原子检查“一人一企业”并创建Member关系。
5. 冻结个人资产，保留原Key。
6. Owner分配额度后，成员才能发起企业资助调用。

### 13.3 企业管理员邀请新用户

1. Owner向未注册邮箱发送企业邀请。
2. 用户完成邮箱验证和账户注册。
3. 系统在同一事务中创建用户、唯一主Key、消费邀请并创建Member关系。
4. 账户创建失败或成员关系冲突时，不能留下半账户或孤立企业关系。
5. 初始Key交付继续遵守已启用的单主Key账户规则。

### 13.4 成员调用API

1. 系统通过Key确定真实调用用户。
2. 服务端解析唯一有效企业关系和成员状态。
3. 检查成员为`ACTIVE`、企业白名单、成员可用额度和Key自设上限。
4. 原子预留成员额度并写入计费快照。
5. 调用上游并按实际用量结算。
6. 多预留部分退回成员额度；异常超额进入原企业异常账并暂停成员。

### 13.5 成员重置Key

1. 成员完成安全验证。
2. 系统确定其唯一主Key。
3. 原子轮换同一Token记录并使旧Key失效。
4. 撤销目标Key建立的旧会话。
5. 新完整Key发送至已验证绑定邮箱。
6. SMTP失败进入待交付状态，并重发同一个新Key。

### 13.6 Root/Admin重置指定Key

1. Root/Admin完成安全验证。
2. 从自己的掩码Key列表选择一个目标Key。
3. 系统校验目标Key确实属于本人。
4. 只轮换目标Key，其他Key不变。
5. 新完整Key发送至本人已验证绑定邮箱。
6. SMTP失败时只重发本次生成的新Key。

## 14. 失败状态与边界处理

| 场景 | 规定行为 |
| --- | --- |
| 企业自动创建失败 | 拒绝企业调用，不回退个人钱包。 |
| 用户已有企业关系 | 拒绝再次加入或创建第二个企业。 |
| 并发接受多个邀请 | 只有第一个成功，其余失败或失效。 |
| 成员已暂停 | 拒绝新企业资助调用，保留登录与查看能力。 |
| 成员有在途任务 | 不允许完成移除，进入等待。 |
| 移除等待超时 | 进入人工处理，不强制删除关系。 |
| 迟到退款 | 退回原企业钱包或尚未关闭的原成员额度。 |
| 成员额度不足 | 拒绝调用，不回退个人资产。 |
| 异常超额 | 记原企业异常账，暂停成员，不扣个人资产。 |
| Key并发重置 | 同一幂等动作只轮换一次。 |
| SMTP失败 | 旧Key保持失效，进入待交付，重发同一新Key。 |
| Key重置后企业仍暂停 | 仍拒绝企业资助调用，重置不能解除暂停。 |
| 加入企业前订单迟到回调 | 进入冻结的个人钱包，不进入企业钱包。 |
| Owner需要删除 | 必须先转移所有权或完成企业关闭。 |

## 16. 非功能要求

### 16.1 安全

- 所有企业资源访问必须在后端验证企业归属和成员关系，防止跨企业IDOR。
- Key、邮箱验证凭证和邮件交付内容不得进入普通日志、URL或管理员响应。
- 所有邀请、重置和邮件重发保留限流、验证码和账户枚举防护。
- 密码、OAuth、Passkey、2FA等现有安全语义不得被本需求削弱。

### 16.2 一致性与可靠性

- 分配、预留、结算、退款和回收必须支持并发且保持账面守恒。
- 支付回调、异步任务轮询、邮件投递和退款必须幂等。
- 数据模型和迁移必须同时支持SQLite、MySQL和PostgreSQL。
- SMTP、缓存或会话撤销等后置步骤失败时，必须留下明确、可恢复、可审计状态。

### 16.3 隐私与可审计性

- 企业账单只展示完成企业管理所需的最少成员数据。
- 请求正文、提示词和响应正文默认不向企业管理员开放。
- 历史流水不能因用户退出、Key轮换或企业关闭被重写或删除。

## 17. 已接受风险

以下风险已经由产品方明确接受，本期不作为阻塞项：

1. 管理视图/企业视图不是接口安全边界。
2. Root/Admin现有每一条有效API Key都可以登录后台。
3. Root/Admin保留多Key，不在本期收敛为单Key。
4. 完整新Key通过邮件正文明文交付，适用于Root/Admin。
5. 数据库Key轮换与外部SMTP投递不能组成原子事务。
6. SMTP最终失败时旧Key保持失效，账户进入待交付状态。
7. Root/Admin可以互相调整企业额度且无需审批。
8. “不能给自己加额度”只是统计约定，不是安全规则。
9. 密码、OAuth、Passkey、2FA等其他登录方式保持现状。
10. 只轮换被选择的Root/Admin Key，其他Key继续有效；这不构成完整账号失窃处置。

风险接受不取消邮箱所有权验证、限流、幂等、审计、会话撤销、租户隔离和敏感信息保护。

## 18. 首版不包含

- 一个用户同时加入多个企业。
- 一个企业拥有多个Owner或多个企业管理员。
- 企业共享订阅；首版只共享企业钱包额度。
- 将管理视图/企业视图升级为服务端接口安全模式。
- 收敛Root/Admin为单Key。
- 修改或移除密码、OAuth、Passkey、2FA等现有登录方式。
- 平台管理员人工调额审批流。
- 企业管理员全局封禁、删除或修改成员平台身份。
- 企业管理员查看成员完整Key、个人余额、个人订阅或请求正文。
- Root/Admin一键轮换全部Key的账号失窃处置流程。
- 具体数据库表、API路径、前端页面结构和迁移脚本；这些属于后续技术设计。

## 19. 验收条件

### 19.1 角色与租户

- [ ] 企业管理员的平台角色仍为普通User，无法访问任何平台Admin接口。
- [ ] Root与Admin能访问约定的全部业务管理功能。
- [ ] Root/Admin不能修改其他Root/Admin的身份或认证信息。
- [ ] Root/Admin各自只有一个独立企业且互不共享账单。
- [ ] 同一用户并发接受多个企业邀请时最多产生一个有效企业关系。
- [ ] 企业接口无法通过修改请求中的企业ID访问其他企业。

### 19.2 计费与额度

- [ ] 企业钱包、成员额度和个人钱包是独立资金账户。
- [ ] 分配、预留、结算、退款和回收后满足企业账面守恒。
- [ ] 并发请求不能超过成员可用额度或重复消费同一额度。
- [ ] 成员额度不足时不会扣个人钱包或个人订阅。
- [ ] 成员不能通过修改Key上限或设置无限额度增加企业资金。
- [ ] 异常超额进入原企业异常账并暂停成员，不产生个人扣费。
- [ ] 成员退出后迟到退款仍退回原企业。

### 19.3 成员生命周期

- [ ] 暂停成员后新企业调用立即被拒绝，但成员仍可登录和查看状态。
- [ ] 存在在途请求、预扣或异步任务时不能完成移除。
- [ ] 移除超时进入人工处理，不会强制删除成员关系。
- [ ] 回收只包括未消费、未预扣额度。
- [ ] 移除完成后个人钱包和订阅恢复，订阅到期时间按冻结时长顺延。

### 19.4 Key与邮件

- [ ] 普通用户、企业Owner和Member并发创建Key时最多只有一个主Key。
- [ ] Root/Admin选择哪个Key就只轮换哪个Key。
- [ ] 目标旧Key轮换后不能调用API或登录，其他Root/Admin Key保持有效。
- [ ] 重置后额度、用量、白名单、企业关系和历史不变。
- [ ] 完整新Key只发送至账户已验证绑定邮箱，不向企业管理员或其他管理员展示。
- [ ] 同一重置请求并发或重试只发生一次轮换。
- [ ] SMTP失败后旧Key仍失效，重试邮件发送的是同一个新Key。
- [ ] Key额度耗尽仍可登录后台。

### 19.5 审计与隐私

- [ ] 成员退出、换企业、Key重置后历史账单归属不变。
- [ ] 企业管理员只能查询自己企业的账单和成员信息。
- [ ] 企业管理员无法读取成员个人资产、认证材料、完整Key和请求正文。
- [ ] 所有调额、分配、回收、暂停、移除、轮换和异常处理都有操作者与请求ID。

## 20. 上线前验证边界

后续实现至少需要完成：

- 角色与权限矩阵自动化测试。
- 企业IDOR和跨租户访问测试。
- SQLite、MySQL、PostgreSQL并发接受邀请、分配、预留、退款和移除测试。
- 同步请求与异步任务在暂停、退出和迟到退款场景下的端到端测试。
- 支付回调在用户加入企业前后发生时的计费快照测试。
- Key并发轮换、目标Key选择、旧Key失效和会话撤销测试。
- SMTP成功、失败、超时、重复回调和重发同一Key测试。
- 个人订阅冻结、反复冻结、到期顺延和解冻幂等测试。
- 企业账面守恒与异常超额审计测试。

仅有前端隐藏、HTTP 200、数据库字段存在或邮件服务商接受请求，都不能单独视为验收通过。

## 21. 非阻塞配置项

以下参数不改变本规格核心模型，可在技术设计或上线配置阶段确定：

- 企业邀请和邮箱验证的具体有效期。
- 成员`DRAINING`进入人工处理的超时时长。
- 邮件自动重试次数、间隔和最终失败告警渠道。
- 异常账的人工处理SLA、减免和补扣操作界面。
- 企业账单导出格式和数据保留时长。
- 企业管理员可见用量字段的最终前端展示方式。

## 22. 当前实现差距（静态证据）

以下是编写本规格时从当前源码确认的差距，不代表完整技术方案：

- 平台鉴权仍按数值角色比较，尚无企业角色维度：`middleware/auth.go`。
- 普通用户单Key和轮换逻辑仍精确依赖普通用户平台角色：`model/token.go`。
- Token更新仍允许用户覆盖剩余额度和无限额度字段：`controller/token.go`。
- 当前Relay计费上下文主要只有用户与Token，没有企业计费快照：`relay/common/relay_info.go`。
- 当前钱包和订阅主要按用户选择资金来源：`service/billing_session.go`。
- 当前日志与异步任务没有完整企业、成员和分配快照：`model/log.go`、`model/task.go`。
- 当前充值和订阅购买路由只要求普通用户登录，尚未拒绝企业成员：`router/api-router.go`。
- 当前Key找回仍采用邮件链接和HTTPS返回完整Key，不符合本规格的邮件正文交付：`controller/misc.go`。

这些差距说明后续需要独立技术设计和迁移计划；本轮未修改源码、数据库或运行配置。
